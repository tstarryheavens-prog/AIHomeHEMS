## 💀 失敗その1：HEMS端末に短周期リクエストを乱れ打ちして機器が完全フリーズ！

これが一番心臓に悪かった失敗です。

我が家のHEMSコントローラは、組み込み向け小型Webサーバー（CenteHTTPd）で動いています。  
「リアルタイムにグラフを更新したいから、5秒おきに全データをスクレイピングしよう！」と考えた私は、以下のような**無慈悲な乱れ打ちコード**を書いてしまいました。

<br>

### ❌ やっちゃダメな失敗コード
```python
# ⚠️ 絶対に真似しないでください！HEMSが死にます！
while True:
    # 5秒おきに複数のHTML/CGIページを一気に連続GET！
    s.get("http://192.168.1.100/e-flow.html")
    s.get("http://192.168.1.100/best5.html")
    s.get("http://192.168.1.100/cost.html")
    s.get("http://192.168.1.100/monitor3.html")
    time.sleep(5)  # 5秒インターバル
```

<br>

### 💥 何が起きたか？
PCや最新サーバーの感覚でリクエストを投げていたのですが、相手は十数年前の設計の貧弱な組み込み機器です。同時TCP接続数もセッション処理能力も極小。

スクリプトを動かして数分後、**壁面に取り付けられたHEMS端末の液晶画面がピキッと固まり、ブラックアウトして完全沈黙しました。**  
PINGすら通らない。ボタンを押しても反応しない。  
「やばい、十数万円の機器を文鎮化させてしまった……？！」と冷や汗が吹き出しました（※最終的にブレーカーを落として強制コールドリブートしてなんとか復旧）。

<br>

### 💡 解決策：事前ソケット疎通確認 ＆ 15秒キャッシュスロットリング
この反省から、以下の2重の防波堤をコードに組み込みました：

1. **事前疎通チェック（Pre-flight Ping）**: HTTPリクエストを送る前に、RAWソケットでポート80が開いているか0.5秒で確認。詰まっていたら即スキップ。
2. **15秒スロットリング**: 15秒以内のアクセスには前回のキャッシュ値を返し、実機へのアクセス頻度を極限まで減らす。

<br>

```python
# ⭕ 改善後の安全なコード（hems_logger.pyより抜粋）
now_ts = time.time()
# ハングアップ防止：15秒以内の連続アクセス時はキャッシュを返却
if now_ts - poll_and_log_all_data._hems_cache["time"] < 15.0:
    return poll_and_log_all_data._hems_cache["grid_w"]

# 事前疎通チェック（0.5秒でポート80が開いているか安全確認）
sock_check = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock_check.settimeout(0.5)
conn_res = sock_check.connect_ex((hems_ip, 80))
sock_check.close()

if conn_res == 0:  # 相手が健康な時だけリクエスト
    # リクエスト処理...
```

## 📉 失敗その2：売電と買電の符号判定ミスで「エネルギー保存則」が崩壊！

HEMSのリアルタイム電力フロー画面（`e-flow.html`）をスクレイピングした時のやらかしです。

Web画面には「2.2kW」という数値が表示されているのですが、**それが「買電（電気を買っている）」なのか「売電（電気を売っている）」なのか**を画面の見た目だけで判定しようとして大失敗しました。

<br>

### ❌ やっちゃダメな失敗コード
```python
# ⚠️ 単に数値をパースして足し算していた
power_val = float(trade_text.replace("kW", "")) * 1000
# 符号を考慮せずプラスとして計上
grid_power = power_val
```

<br>

### 💥 何が起きたか？
昼間に太陽光が4.0kWフル発電し、蓄電池も満充電で、余った2.2kWを系統へガンガン売電している絶好調の瞬間。  
ダッシュボードを見ると、なぜか**「家全体の消費電力：6.2kW（超爆食い！）」**と表示されている……！

売電の `-2.2kW` をプラスとして足してしまったため、発電すればするほど家で電力をバカ食いしているという**怪奇現象**が発生してしまったのです。

<br>

### 💡 解決策：隠しプロパティと矢印属性を泥臭く抽出
CenteHTTPdのJavaScriptコードを解析したところ、タイトルの文字列（`tTradeTitle`）だけでなく、**矢印の向きを表す内部変数 `iAddTradeArrow`（"in" or "out"）**が存在することを発見！

```python
# ⭕ 改善後の判定ロジック
trade_title = d_flow.get("tTradeTitle", "買電")
arrow_dir = d_flow.get("iAddTradeArrow", "out")

if "売電" in trade_title or arrow_dir == "in":
    grid_w = -int(round(trade_val))  # 売電はマイナス！
else:
    grid_w = int(round(trade_val))   # 買電はプラス！
```
これでようやくグラフのエネルギー保存則がピッタリ整合するようになりました。

## 🔋 失敗その3：深夜21時に即フル充電！バッテリー寿命を縮めるアンチパターン

「深夜電力（16.30円）が始まったら充電すればいいんでしょ？」と単純に考えて組んだ初期のスケジューラーです。

<br>

```yaml
# ❌ 初期にやらかしていたダメ設定
electricity_tariff:
  night_start_hour: 21   # 21:00開始
  charge_start_hour: 21  # 21:00に即充電スタート！
```

<br>

### 💥 何が起きたか？
我が家のニチコン蓄電池は急速充電能力が高いため、21:00に充電を開始すると、**夜中の23:00には100%満充電**になってしまいます。  
その結果、朝7:00に家族が起き出して電気を使い始めるまで、**約8時間ものあいだ「100%満充電状態のまま高温放置」**されることになりました。

リチウムイオン電池の劣化原因の第1位は「満充電状態での放置」です。高価な蓄電池の寿命を自ら縮める最悪の運用をしていました。

<br>

### 💡 解決策：朝の使用ピーク直前を狙う「JIT充電（Just-in-Time）」
充填完了時刻を「朝6:30」に設定し、逆算して**午前3:00から充電を開始するアルゴリズム**に変更しました。  
満充電になった瞬間に朝の自家消費が始まるため、100%保持時間をほぼゼロに抑えることができます！

## 🔒 失敗その4：SQLiteの `database is locked` で常時監視ロガーが憤死

秒単位でデータを蓄積するために SQLite を採用したのですが、運用開始して数時間後にロガースレッドが突然死しました。

```
sqlite3.OperationalError: database is locked
```

### 💥 原因
- **スレッドA（監視ロガー）**: 1秒おきに最新テレメトリを `INSERT`
- **スレッドB（Streamlit UI）**: 画面描画のために過去48時間分の数万件データを `SELECT`

SQLiteのデフォルト設定（Rollback Journalモード）は、書き込み時にデータベース全体を排他ロックします。UI側が重い集計クエリを発行している最中にロガーが書き込もうとしてタイムアウトし、クラッシュしていたのです。

<br>

### 💡 解決策：WALモード（Write-Ahead Logging）の有効化
SQLite接続時に以下のPRAGMAコマンドを発行することで、**「読み取りと書き込みの完全並行処理」**が可能になり、ロック衝突が完全に撲滅されました！

```python
# ⭕ SQLite初期化時にWALモードを有効化
conn = sqlite3.connect("hems.db", timeout=20.0)
conn.execute("PRAGMA journal_mode=WAL;")  # これ一行で世界が変わる！
conn.execute("PRAGMA synchronous=NORMAL;")
```

## 📡 失敗その5：Wi-SUN USBドングルによるスマートメーターBルート直受信の挫折

当初は、電力会社のスマートメーターと直接「Bルート通信（Wi-SUN）」を行おうとして、USBドングル（ROHM製など）を購入してシリアル通信スクリプト（`broute_collector.py`）を書いていました。

しかし……
- スマートメーターとHEMS親機がすでにペアリングされているため、電波の競合や認証セッションの切断が多発
- ドングルのファームウェアやシリアルポートの切断復帰がシビア
- 家の壁の断熱材や鉄骨のせいで、メーターとの通信感度が不安定

**「すでにスマートメーターと有線/無線で安定接続してくれている既存のHEMS端末があるんだから、その端末からデータを引っ張ればいいじゃん！」**  
と気づき、ドングル直受信を諦めてHEMS Webスクレイピング＋ニチコン直通信のハイブリッド構成にピボットしました。

結果として、余計な追加ハードウェアも不要になり、通信の安定性は段違いに跳ね上がりました。「なんでも自前で直通信しようとしない」のも重要な教訓でした。

## 📢 まとめ＆次回予告

自作HEMS開発でやらかした痛恨の失敗ワースト5をご紹介しました！

2. **電力フローの符号は、タイトルだけでなく内部の矢印属性まで見て判定せよ！**
3. **蓄電池の充電は深夜開始ではなく、朝の使用直前に完了させよ！**
4. **時系列ログをSQLiteに書くなら、何が何でもWALモードを有効にせよ！**
5. **無理にスマートメーターと直接戦わず、既存の安定した機器を活用せよ！**
